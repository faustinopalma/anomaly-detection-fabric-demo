Anomaly Detection on Microsoft Fabric

Simulated data, controlled faults, an ONNX model running in Fabric, and actions triggered by detections.

This project demonstrates the complete anomaly detection flow. The central step is creating a custom model, loading it into a Fabric KQL database, and running it as data arrives.

01 / Flow

From data to action

The simulator generates measurements from illustrative machines and injects controlled faults: a sudden spike, a gradual drift, or a stuck value. Data enters Fabric through an Eventstream endpoint, which writes it to the raw_telemetry table in the Eventhouse's KQL database.

The model analyzes sequences of measurements and produces an anomaly score. Detections are saved in anomalies, displayed on the dashboard, and used by Fabric Activator rules to trigger configured actions.

02 / Creation

Train and export the model

The detector is a Transformer autoencoder, a neural network that learns to reconstruct normal operating sequences by considering multiple signals together and how they evolve over time. The difference between the input and its reconstruction becomes the score used to detect anomalies.

  1. Prepare the data. Build windows of 64 time steps, with one column per signal. The scaler saves each signal's mean and standard deviation so normalization stays consistent between training and inference.
  2. Train and select the threshold. The network learns from normal data. Example faults are injected into separate data to compare model variants and select the detection threshold. Training can run locally or on Azure Machine Learning.
  3. Export to ONNX. ONNX is a portable format describing the model's operations and weights. The export also includes score calculation: for the saved CNC models, the mean squared error over time for each signal, followed by the maximum of those means.

The exporter produces an ONNX file with reduced-precision FP16 weights, checks its size, and compares ONNX Runtime results with PyTorch results. The project uses a 1 MiB budget for the Base64-encoded model to fit the chosen loading path.

With local dependencies installed, this command trains one of the included models and saves its artifacts in models/transformer_ae_small__M-003/:

python tools/cnc_ae_lab.py M-003 --epochs 18 --save

03 / Loading

The model in the models table

The ONNX file is loaded into the models table in the Eventhouse's KQL database. The registration script reads the training artifacts and inserts them into a row with the model name and version.

model.fp16.onnxNetwork and score calculationpayload: Base64-encoded ONNX bytes

With the Fabric tables prepared and the local environment configured, this command registers one of the included models:

python tools/05_register_model.py models/transformer_ae_small__M-003

The script resolves the workspace and database from local configuration. Each registration increments the version; the KQL function latest_model() selects the latest version for that name. The threshold is stored in metadata: updating it requires a new registration while keeping the model weights.

04 / Execution

From microbatch to detection

An update policy is a KQL rule that runs a transformation when a table receives data. Here it connects raw_telemetry to the scoring function and writes the result to anomalies.

Ingestion collects data into microbatches, small groups processed together, with a configured maximum batching time of one minute. This queued path supports the Python plugin in update policies. Detection latency also includes window formation and model execution.

  1. Build windows. The KQL function aligns signals in the new batch and adds the preceding samples needed to complete the sequences required by the model.
  2. Load into memory. python() receives the windows and the model row. It decodes payload and creates an ONNX Runtime session.
  3. Compute scores. Values are normalized with the registered scaler. ONNX Runtime runs the model and returns one score per window.
  4. Make the decision. KQL compares the score with the threshold and applies the activity filter, selecting windows with a sufficient operating level. It saves detections with their time interval and model version.

To enable this path, enable the Python plugin in the Eventhouse/KQL database, use an image with ONNX Runtime, and apply the KQL scripts for tables, functions, and policies.

Code: ingestion · scoring · policies. Requirements: Python plugin.

05 / Actions

Connect detections to a rule

Fabric Activator evaluates a query over detections and triggers an action when the configured condition is met. For example, group anomalies by machine and send a Teams message when the count exceeds a threshold.

In the Fabric portal, create an alert from a KQL query or a Real-Time Dashboard tile. Set the evaluation frequency, condition, recipients, and action: email, Teams, a Fabric activity, or a Power Automate flow. The demo panel lets you inject a fault and compare it with detections returned by Fabric.

06 / Synthetic data

Generate new sequences from a sample

The project's second topic is creating synthetic data that reproduces the statistical behavior of a reference sample. Consider a process with work cycles and idle periods: both signal values and their changes over time need to be reproduced.

  1. Prepare the sample. Align signals over time, choose the sampling frequency, and separate operating phases.
  2. Measure its characteristics. For each phase, study the mean, variability, and distribution of values; then cycle durations, idle periods, correlations between signals, and autocorrelation, the relationship between successive values.
  3. Generate new sequences. The generator uses these characteristics to produce new cycles and values. For example, autocorrelation makes each sample depend partly on the preceding one, preserving temporal continuity.
  4. Compare statistics. Measure the same properties in the outputs as in the reference sample. Differences indicate which parameters or parts of the generator need adjustment.

In the repository, cnc_build_profile.py extracts a phase-specific profile containing signal statistics, durations, and autocorrelation; cnc_engine.py uses it to generate data. The synthgen pipeline develops a learned approach: a transition model generates phases, a phase-conditioned diffusion model generates signals, and a timing model assigns measurement timestamps. Diffusion learns to transform noise into sequences similar to the sample.

Generated traces feed detector training and the simulator. Controlled faults are added to test the response of the complete flow.
